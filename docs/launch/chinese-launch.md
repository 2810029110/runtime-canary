# 中文社区首发文案

## V2EX 标题

```text
[开源] Runtime Canary：Coding Agent 的 --version 正常，真的等于能用吗？
```

## V2EX 正文

最近在整理 Coding Agent CLI 的运行环境时，我发现一个很常见但容易被忽略的
问题：`--version` 正常，只能证明找到了可执行文件并成功启动进程，不能证明
认证、网络、沙箱、工具调用和清理链路真的可用。

所以我做了 Runtime Canary，一个面向 Coding Agent runtime 的确定性预检工具。
Live Doctor 会执行五层检查：

```text
发现可执行文件 -> 启动 -> 完成任务 -> 验证文件证据 -> 清理隔离环境
```

它会在隔离工作区中生成随机 token，要求 runtime 通过自己的工具写入指定 JSON，
再由测试框架独立验证文件。即使进程退出码是 0，只要没有生成正确证据，仍然会
判定失败。超时时还会终止完整进程树，并报告清理是否完成。

目前可以区分认证、网络、权限/沙箱、配置、超时、缺失证据和清理失败，并给出
下一步建议。仓库内置了确定性 fixture，不需要付费模型请求就能复现这些路径。

能力边界也写在 README 首屏：当前 Codex 有 live adapter，Claude Code 只有
probe；工具不会安装 CLI、执行登录或管理凭据。

项目地址：

https://github.com/2810029110/runtime-canary

更希望得到大家对以下问题的反馈：五层 Canary 契约是否合理、隔离边界是否清晰、
下一个最值得真实验证的 runtime 是什么。

## 长文成稿

我们通常如何判断一个开发工具是否安装成功？找到命令，运行 `--version`，看到
版本号，然后继续工作。

对于普通 CLI，这往往足够；对于会访问模型、调用工具、启动 MCP、写入工作区并
派生子进程的 Coding Agent，这个检查只覆盖了最浅的两层：发现与启动。

真正影响开发的故障发生在后面：认证已经过期，但版本命令不需要认证；企业代理
允许本地命令启动，却阻断了模型连接；沙箱可以读取项目，却不能写入；Agent
正常退出，却只描述了应该修改什么，没有实际调用工具；超时以后，孙进程仍留在
后台占用端口。

Runtime Canary 的思路不是再写一份静态环境检查表，而是执行一个很小、结果完全
确定的真实任务。Live Doctor 会创建隔离工作区，生成随机 token，要求 runtime
通过自身工具把它写入指定 JSON 文件，再由独立 verifier 检查文件是否存在、
token 是否匹配。最后，它还会确认隔离工作区已经删除。

因此，一次 live canary 会产生五个可观测检查点：

1. 是否发现可执行文件；
2. 是否成功启动 runtime；
3. 是否完成 Agent 任务；
4. 是否生成匹配的确定性文件证据；
5. 是否清理隔离工作区和超时进程树。

这带来一个重要区别：退出码为 0 不再等于测试通过。如果缺少文件、token 不匹配，
或者清理失败，Doctor 都会给出独立结论。

为了让测试框架本身可以在没有付费账号时开发，项目提供了确定性 fixture，可以
稳定复现认证、网络、权限、配置、证据缺失、敏感信息输出和进程树超时。README
中的终端动图就是由真实 fixture 输出生成，并明确标注为受控场景。

当前项目仍然保持清晰边界：Codex 已实现 live adapter，Claude Code 只有 probe；
Runtime Canary 不负责安装厂商 CLI、不执行登录、不创建或刷新凭据，也不自动修改
用户配置。它验证的是“现有环境能否完成任务”，不是替厂商完成账号管理。

如果你也维护 Coding Agent 或在 CI 中运行 Agent 工作流，欢迎检查这个五层契约
是否覆盖了你遇到的失败方式：

https://github.com/2810029110/runtime-canary
